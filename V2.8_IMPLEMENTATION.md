# Agentic-AI V2.8 — Live Execution Observatory

V2.8 adds a production-style observability surface while preserving the core security boundary:

- System 2 is local-only and proposal-only.
- System 1 remains the execution authority.
- Council decisions are fail-closed when policy requires it.
- Tool permission checks remain mandatory.
- Executor, observer, verifier, evaluator and recovery data are exposed in the UI.
- Existing backend API contracts are preserved.

- `GET /api/tasks`
- `GET /api/agent/runs`
- `GET /api/agent/{run_id}`
- `GET /api/agent/{run_id}/trace`
- `POST /api/agent/{run_id}/cancel`
- `GET /api/brain/system1/providers` through brain status/provider data
- `GET /api/brain/system2/discover`
- `POST /api/brain/system2/local`
- `PUT /api/brain/models/active`
- `PUT /api/brain/system1/policy`

## Security invariants

The UI must never expose a control that lets System 2 execute a tool directly. The frontend is an observability/control client only; enforcement remains in the backend AgentKernel and System 1 Council.

A displayed `AUTHORIZED` state means the recorded System 1 council allowed the guarded boundary. It does not bypass backend authorization.

## Run

Backend:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Frontend:

```bash
cd frontend
npm install
npm run dev
```

Open the Vite URL and use the Agent tab to select persisted runs.

## Important V2.8 limitation

The existing `/api/agent/run` endpoint remains request/response based. The observatory can live-poll any run that is active or persisted, but starting a new run still returns after the current kernel call completes. A future asynchronous-run phase can add a `202 + run_id` start endpoint without weakening System 1 authority.
